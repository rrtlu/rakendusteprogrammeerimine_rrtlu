Video summaries

1.1 Philip Roberts - What the heck is the event loop anyway? (JSConf EU 2014)

This talk has a really good live demo and visualisation of what the JS runtime looks like. It gives a great overview of JavaScript being single threaded, with one call stack and one task queue. It walks you through how setTimeout does not execute code after X milliseconds, merely adds a callback to be executed at some point. The timer is stored by the browsers Web API. Once it elapses the callback is pushed to the queue. From here the only thing that will move code from the queue to the stack is the event loop. It also shows how any blocking code (like while (true)) will lock up the whole page because the event loop will never get to the queue.

What I learned:

The event loop isn’t part of JavaScript itself but part of the host environment (browser, node)
setTimeout(fn, 0) doesn’t mean immediately, it means once the stack is empty and the previous tasks have been completed.
Because rendering is on the same thread slow synchronous code will cause the UI to lock. This is why we have to split up intense operations.
Stack overflows occur due to infinite recursion, not async code.

1.2 Shelley Vohr - Asynchrony: Under the Hood (JSConf EU 2018)
Shelley covers all the async patterns in JavaScript (callbacks, promises, generators, async/await) and explains how they work underneath. This includes how data is passed between the stack and the event loop, how intermediate values are lost and error handling within each pattern. She also shows that promises and async/await don’t actually result in faster code but just cleaner code. Async/await in particular has a lot of gotchas. Promises and async/await aren’t any faster than each other, and async/await hides a lot of issues. If you forget to await then your error will be lost and you’ll receive a promise object. Also, using await within loops will cause performance issues. She also briefly mentions async in the future.

What I learned:

Callbacks are the oldest and least advanced option. They offer a lot of flexibility but error handling and ordering must be handled manually and easily breaks (callback hell).
Promises are objects that have a state (pending, fulfilled, rejected). Await simply pauses execution of the function, and returns to the promise. It does not block the thread.
If you forget to await you’ll get a promise object (you won’t get the value). Your error will be lost (silent bug).
Awaiting within loops causes performance issues. To get parallelism you need to use Promise.all().
Try/catch only works where you await, elsewhere you should use .catch().

1.3 My pick: Jake Archibald - In The Loop (JSConf.Asia 2018)

Jake explains in much more depth the event loop concepts mentioned in the first video. He explains what the task queue is and what the microtask queue is. He also explains how the rendering works and requestAnimationFrame. He shows how promise callbacks are microtasks and therefore will execute before rendering and before the next setTimeout. Infinite microtasks will stop the browser rendering. He also explains why using setTimeout within loops causes bad rendering and why we should use requestAnimationFrame.

What I learned:

There are two queues, with the microtask queue having higher priority. Microtasks (Promise.then, queueMicrotask) will all be executed before anything is rendered or the next macrotask is executed.
This means that if we use Promise.resolve().then(...) recursively we will cause rendering to be starved.
Request animation frame is executed just before rendering. It should be used for these types of visuals. Using setTimeout(..., 0) within loops causes animations to be jerky.
Changes to the DOM are batched and executed during rendering. So multiple style changes consecutively in the same task will not cause multiple renders.
All three talks taught me that asynchronous code isn’t faster, it’s a way of not blocking. All three talks gave me a clear understanding of why the queue and stack matters and why using await within a loop can be slower than making parallel requests.
